大规模 GPU 训练与多级 Scaling LadderLarge-scale GPU training and model ladders

我参与大规模 GPU 集群预训练，并在小、中、大三级模型上比较数据配方和训练配置。Scaling Ladder 先用较小模型检验想法，再到更大模型上复核；每组实验都需要记录参数规模、训练 Token、批量大小和学习率调度。I participate in large-scale GPU pretraining and compare data recipes and training settings on small, intermediate, and larger models. A scaling ladder tests an idea at lower cost before checking it at a larger scale. Each comparison needs a record of model size, training tokens, batch size, and learning-rate schedule.

Scaling Law 部分关注损失如何随参数规模、数据量和计算预算变化。我比较不同配方的变化趋势，区分对已有实验点的拟合和对未参与拟合规模的预测，也检查同一配方的优势是否只出现在某个规模或训练阶段。For scaling-law studies, I examine how loss varies with parameter count, data volume, and compute budget. I compare trends across recipes, distinguish fitting observed runs from predicting held-out scales, and check whether a recipe’s advantage is limited to a particular model size or training stage.

比较指标包括训练和验证损失、Benchmark 得分、有效 Token 吞吐、训练稳定性、配方排序及外推误差。Chinchilla 和 OLMo-ladder 是相关的公开方法参考；引用它们不代表披露公司配置、内部结果，或使用了相同实现。The comparisons track training and validation loss, benchmark scores, effective-token throughput, training stability, recipe rankings, and extrapolation error. Chinchilla and OLMo-ladder are public references for the methods. Citing them does not disclose company settings or results, or imply an identical implementation.

Benchmark 与 BPB 评估方法Task benchmarks and BPB evaluation

我参与预训练 Benchmark 和评测流程开发，对不同 Checkpoint、数据域和训练配方进行评估。知识与推理任务反映模型的任务表现，损失指标反映模型预测指定文本的能力，两类结果一起看。I contribute to pretraining benchmarks and evaluation workflows for comparing checkpoints, data domains, and training recipes. Knowledge and reasoning tasks measure task performance; loss measures how well a model predicts a specified text distribution. I examine both.

BPB（Bits-per-Byte）是按字节归一化的评估方法：累加被评分 Token 的负对数似然，换成以 2 为底，再除以对应文本的 UTF-8 字节数。若 NLL 使用自然对数，则 BPB = NLL /（ln 2 × 字节数）。只作为上下文的 Token 和未评分的 Padding，不计入对应分子与分母。Bits per byte (BPB) normalizes evaluation loss by text length in bytes. Sum the negative log-likelihood of the scored tokens in base 2, then divide by the UTF-8 byte count of the corresponding text. With natural-log NLL, BPB = NLL / (ln 2 × byte count). Context-only tokens and unscored padding are excluded from the corresponding numerator and denominator.

比较 BPB 时，需要对齐文本内容、规范化方式、上下文窗口、边界处理、评分掩码和聚合方式。按字节归一化可以减轻不同 Tokenizer 粒度带来的单位差异，但不能消除分词和评测协议本身的影响；结果仍要结合分域损失和任务得分解释。BPB comparisons need consistent text, normalization, context windows, boundary handling, scoring masks, and aggregation. Byte normalization reduces the unit mismatch between tokenizers with different granularities. It does not remove tokenizer or evaluation-protocol effects, so domain-level losses and task scores still matter.

BPB = −∑t ∈ S ln pθ(xt | x<t)ln 2 · BS

S 为实际计分的 Token 集合，B_S 为其对应原始文本的 UTF-8 字节数；语料整体按总 NLL/总字节数聚合，与逐文档 BPB 的简单平均不同。S denotes scored tokens and B_S the UTF-8 byte count of the corresponding original text. Corpus-level total NLL divided by total bytes is different from an unweighted mean of document BPB values.

Document Packing、数据混合与质量分层Document packing, data mixtures, and quality tiers

Packing 实验比较文档边界、长度分布和 Padding 策略对计算利用率与训练任务的影响。把多个文档放进同一序列后，还需要检查 Attention Mask、Position ID 和 Loss Mask：这些设置决定模型能否使用跨文档上下文，以及哪些位置参与训练。Packing experiments compare how document boundaries, length distributions, and padding choices affect compute utilization and the training task. When documents share a sequence, attention masks, position IDs, and loss masks determine which context is available and which positions contribute to training.

我结合领域分类、质量分层、分桶采样、Data Mixture 和数据增强，比较语料组成与呈现方式。Nemotron 的公开工作提供了质量分类、去重和合成数据的参考；具体配方是否有效，仍通过可比预算下的训练和评测来判断。I use domain classification, quality tiers, bucketed sampling, data mixtures, and augmentation to compare corpus composition and presentation. Public Nemotron work provides references for quality classification, deduplication, and synthetic data. The value of a particular recipe is tested through training and evaluation at comparable budgets.

除了模型效果，还记录有效 Token 比例、Padding 占比、序列长度分布、训练吞吐和分域验证损失。更多有效 Token 与更好的数据内容可能带来不同收益，需要分开判断；配方对比也要核对各数据源的采样权重和实际训练暴露量。Alongside model performance, I track effective-token fraction, padding fraction, sequence-length distribution, throughput, and domain-level validation loss. Processing more useful tokens and improving the content of the data can produce different gains, so they need to be distinguished. Mixture comparisons also check sampling weights and the actual training exposure of each source.

预训练数据管线开发与联调Pretraining data-pipeline development and integration

我参与语料预处理、Tokenization、数据分片、Document Packing 和 DataLoader 的开发与联调，将候选数据策略接入已有训练平台。主要检查文档经过处理后，是否形成了符合预期、能够被训练端正确读取的样本。I contribute to corpus preprocessing, tokenization, sharding, document packing, and data loading, integrating candidate data strategies into an existing training platform. The work checks whether processing produces the intended samples and whether training consumes them correctly.

联调时核对 Token 和样本数量、分片与索引的一致性、文档边界和掩码行为，并从训练端复核实际数据分布。这些检查有助于区分数据策略的效果与样本构建、加载或评测口径变化造成的差异。Integration checks cover token and sample counts, shard/index consistency, document boundaries, and masking behavior, followed by verification of the data distribution seen by training. These checks distinguish data-policy effects from changes in sample construction, loading, or evaluation.

同时关注数据准备与读取吞吐、实际采样分布和训练输入一致性，并记录数据版本、训练配置与 Checkpoint 的对应关系。候选配方接入后，再通过预训练对照和 Benchmark 评测检查效果。I also track data-preparation and loading throughput, realized sampling distributions, and input consistency, and keep data versions linked to training settings and checkpoints. Once a candidate recipe is integrated, controlled pretraining runs and benchmark evaluation test its effect.

跨尺度对照与结果复核Cross-scale comparisons and validation

小模型上的改进能否延续到大模型，是这项工作反复遇到的问题。我把模型规模、训练预算、数据配方和 Checkpoint 位置放在一起比较，检查效果是否依赖某个预算、训练阶段或评测设置。A recurring question is whether an improvement on a small model persists at a larger scale. I compare model size, training budget, data recipe, and checkpoint position together, checking whether an effect depends on a particular budget, training stage, or evaluation setup.

比较损失曲线和分域能力时，保持其余变量尽量一致，并区分 Token 预算与计算预算。计算量按具体架构、序列长度和执行策略核算，说明是否计入前向、反向、激活重计算与优化器更新。MoE 每个 Token 激活的计算与总参数的状态存储是两个问题；Attention 的计算也取决于序列结构、掩码和实现，不能只看参数量与 Token 总数。Loss and domain-level comparisons keep other variables as consistent as possible and distinguish token budgets from compute budgets. Compute accounting depends on architecture, sequence length, and execution policy, with the scope of forward, backward, activation recomputation, and optimizer updates stated explicitly. In MoE, per-token active computation differs from state storage for all parameters. Attention cost also depends on sequence structure, masks, and implementation, beyond parameter count and total tokens.

报告 FLOPs 时，注明是模型理论计算量，还是包含重计算等额外工作的执行计算量；报告 Token/s 时，注明有效或实际处理 Token，以及全局或单卡口径。实际耗时还受到未被重叠隐藏的通信、数据读取和同步等待影响。口径对齐后，再比较整体趋势、任务差异与配方排序反转，并用未参与拟合的规模或阶段检验外推。FLOP reports distinguish model-operation estimates from execution counts that include extra work such as recomputation. Tokens per second specifies effective or processed tokens, and global or per-GPU scope. Elapsed time also includes exposed communication, data loading, and synchronization. With those definitions aligned, I compare overall trends, task differences, and recipe-rank reversals, and test extrapolation on scales or stages excluded from fitting.

这些比较帮助决定下一步做什么：扩大哪组实验、补充哪些对照，以及怎样处理不同指标之间的取舍。OLMo-ladder 将中间损失特征与任务表现分开建模，是这一方向的公开方法参考。These comparisons help decide which experiments to scale up, which controls are missing, and how to handle trade-offs between metrics. OLMo-ladder, which models intermediate loss features separately from task performance, is a public reference for this approach.
